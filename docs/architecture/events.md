# Event Log and Convergence

Records semantic events and converges concurrent changes deterministically.

## Responsibilities

- Turns semantic deltas and identity merges into **events** with ids derived from content, clocks consistent with the commit history, an author fingerprint, an author kind and opaque labels.
- Records live events in the write-ahead log and publishes them as one **event tape** per publish, indexed by commit.
- Reconstructs, on demand and identically on every machine, the events of commits made without Gedo.
- Filters events by labels, author kind, agent and fingerprint, for the tools built on Gedo (ADR-0013).
- **Re-attaches** tapes to commits rewritten by a rebase, an amend or a server-side squash or rebase merge, reports **detached** tapes for the 90-day retention, and fills the event cache when new events arrive (ADR-0016).
- **Converges** the work of several sides over a common base with the **tree CRDT**: members of a structure behave as a set, moves, renames and edits of different parts commute, an event present on several sides applies once, and incompatible changes are reported as conflicts, never resolved silently (ADR-0017).
- Later releases add **semantic lanes** (refactor and feature, `gedo publish --split-lanes`), **virtual streams** (`gedo stream <name>`, whose events inherit the stream's author and labels), and the deterministic **sequencer** shared by the merge driver, the shadow merge and the relay.
- Does not read or write files; the WAL and the collections are reached through ports.

## Behavior

**Events.** An event names its target entity, its operation (a `SemanticDelta` of feature 003, or an identity merge with the kept and merged ids), the entity's structural hash after it (none for a tombstone or a merge), a clock, the author and the labels, and whether it was recorded live or reconstructed. Its `EventId` is a UUID version 8: BLAKE3 in key-derivation mode (`gedo event id v1`) over the postcard encoding of all those fields, truncated to 16 bytes. Equal content gives equal ids everywhere, so a retried publish or a graft stores an event once ([ADR-0014](../adr/0014-event-format-content-derived-ids-history-clocks-and-three-co.md)).

**Clocks.** A clock is `(generation, sequence)`. A commit's generation is 1 for a root and one more than its highest parent otherwise. A reconstructed event takes its commit's generation and its position among the commit's events; a live event recorded on top of a commit takes that commit's generation plus one and the next sequence of the log. An event of a commit is therefore later than every event of its ancestors, live events are later than their base's, and `(clock, id)` orders any set of events the same way on every machine. `EventLog` keeps the generations it computed in memory and walks only unknown ancestors.

**Authors and labels.** The author fingerprint is BLAKE3 (`gedo author v1`) of the Git e-mail with ASCII whitespace trimmed and ASCII letters lowercased; the e-mail is never stored. The author kind is a person, or an agent with an identifier (1 to 64 bytes of `[a-z0-9._-]`, starting with a letter or digit) whose events carry the fingerprint of the Git identity it runs on. Labels are at most 16 pairs, keys with the agent identifier rule and values of 1 to 256 bytes of UTF-8 without control characters, sorted by key, stored and returned unchanged. A `RecordingContext` is built from values or from the texts of `GEDO_AGENT` and `GEDO_LABELS` (`key=value` pairs separated by `,`, with `\,` and `\\` escapes); a tool cannot record a key with the reserved prefix `gedo.`. Reconstructed events are a person's and carry no labels.

**Record and publish.** `record` appends one `WalRecord::Event` per event to the WAL. `publish(commit)` reads the log, deduplicates by id, refuses more than 65,536 events (the log is kept), and writes three content-addressed collections in order: `refs/gedo/events` (entry: the event id), `refs/gedo/tapes` (entry: the tape id; the tape lists the event ids in recording order and names no commit) and `refs/gedo/commit-tapes` (entry: the commit id followed by the tape id). Only then does it truncate the log through the last record it read, so events appended meanwhile stay. Every step is idempotent: after a crash, publishing again gives the same data. Chains written on several machines join by union, like every collection.

**Reading.** `tapes_of(commit)` reads the index entries of the commit from one fan-out directory; `tape` and `event` read records, check their format, invariants and that their content matches their id; a tape or event named by an index or a tape but missing locally (a partial fetch) is `Missing`. `events_of_commit` returns the tapes of a commit followed by the remainder (below), or, when it has none, the events reconstructed from its identity record: its deltas against the first parent, then its identity merges, with the ids as recorded at the commit (never resolved through later aliases), the commit author and the commit's generation. Reconstructed events are never written to `refs/gedo/*`. `filter` scans the stored events and returns the matching ones in the total order.

**Re-attachment.** `reattach_rewritten(pairs)` takes the `(old, new)` pairs of Git's `post-rewrite` hook; `reattach_new(commits, tips)` takes commits that arrived without pairs (a fetch after a server-side squash or rebase merge), whose candidates are the **detached** tapes, indexed for no commit reachable from `tips`. A commit that already has an index entry is skipped. For a pair, equal **semantic signatures** of the old and new commit (BLAKE3 over their deltas, merges and result hashes, never stored) attach every tape of the old commit. Otherwise `gedo_crdt::match_commit` folds the candidate events per entity in their total order; a change matches the latest event that leaves the entity in the same state, the earlier ones are superseded, entities created then removed or changed then changed back are neutral. With a pair, a tape attaches when one of its events is matched or superseded; without one, when all its events are matched, superseded or neutral and at least one is matched or superseded. A creation in the commit with no candidate events matches the branch entity with the same kind, qualified path and final hash, and the two ids are **linked**. Commits are processed in generation order; a tape attached to an ancestor in the same call is no candidate for its descendants. Only `refs/gedo/commit-tapes` is written, in one write per call ([ADR-0016](../adr/0016-re-attachment-by-entity-state-with-a-semantic-signature-fast.md)).

**Remainder.** For a commit with tapes, `events_of_commit` matches its changes against its own tapes and returns, after them, the reconstructed events of the changes they do not account for (an amend that added code, a resolved conflict), then the links as reconstructed identity merges with the lower id kept (ADR-0007). It is empty for a commit its tapes cover, and, like reconstruction, needs the commit's identities.

**Retention.** `detached(tips, now, grace_days)` lists the tapes indexed for no reachable commit, with the time this machine first saw each detached (one record in the cache's `retention` namespace, rewritten in one transaction; an attached tape leaves it) and whether the grace period (`DEFAULT_GRACE_DAYS`, 90) has passed. Without a cache, or with a refused record, every tape is dated `now`, so none is eligible. Nothing is removed: that is `gedo gc`.

**Event cache.** With a symbol cache (`EventLog::with_cache`), a publish also keeps the records of its events in the cache's `events` namespace, after the index entry and before the log is truncated, and `event`, `events`, `events_of_commit` and `filter` read the cache first and the collection on a miss, keeping what they read, so a filter reads one database instead of one object per event ([ADR-0015](../adr/0015-packed-batch-writes-and-an-event-cache.md)). Cached records go through every check of stored ones; a refused entry is read again, and a cache failure is only a warning. `fill_cache` reads every stored event the cache lacks, in batches of 1,000, so the first filter after new events arrive (a fetch, a merge of `refs/gedo/*`) reads no event object.

**Tree CRDT.** An entity's state has its kind and five parts compared on their own: **presence**, **place** (unit, file and container path), **name**, **signature** hash and **body** hash, with its structural hash when known. The qualified path is the container path and the name, split at the last `::` outside angle brackets; a method's container path is its type's. `TreeState::from_maps` builds a state from identity results. `fold` applies a side's events over a base: each event once (by id), ids resolved through identity merges (the caller's and every side's, lower id kept), in the total order; a creation sets presence, kind, place and name, a move place and name, a rename the name, a signature or body change that hash, a removal presence. An entity created and removed on one side is neutral and leaves no trace; an event about an entity neither in the base nor created earlier on its side is `TreeError::UnknownEntity`. `converge` (or `converge_with`, with the caller's identity merges) takes a base and any number of sides: a part changed by no side keeps the base value, a part changed by sides that agree takes their value, distinct values give a `Conflict` and the part keeps its base value. Place and name commute with everything and signature with body (the structural hash of an entity combined from several sides is then unknown); a removal against a change of another part, a container removed while another side adds or moves a member into it, and different entities with the same kind and qualified path added on several sides (implementation blocks excepted) are conflicts; entities added on several sides with equal structural hashes are one entity, linked with the lower id kept. Each conflict names the entity, its kind, the base value and each distinct value with its sides (by input position) and the events that set it. The result depends only on the base and the set of events of each side ([ADR-0017](../adr/0017-tree-crdt-as-a-three-way-convergence-of-entity-parts.md)).

**Converging commits.** `converge(base, sides)` takes a base commit and, per side, a tip and live events on top. The commits of a side are those reachable from its tip and not from the base, visited from the highest generation down and processed in generation order; their events come from `events_of_commit`, so published commits give their live events with authors and labels. The base state holds the files the sides' commits changed, and the whole base when an event names an entity outside them. The result is the convergence with the commits and event counts of each side; nothing is written.

**Observability.** `tracing` events: events recorded (debug), events published (info, with the commit, the tape and the count), publish refused because the tape is too large (warn), events reconstructed (debug), tapes re-attached (info, with the commit, the count and whether the fast path was used), re-attachment done (info), changes not matched (debug), detached tapes (info), event cache filled (info), retention record refused (warn), sides converged (info, with the base, the sides, the events and the conflicts), side read (debug).

## Interfaces

- Convergence is called by the merge driver (FEAT-070), the shadow merge (FEAT-074), the sequencer (FEAT-069) and virtual streams (FEAT-068).
- Re-attachment, the retention report and `fill_cache` are called by the `post-rewrite` and fetch hooks (FEAT-090, FEAT-091), the daemon's background fetch (FEAT-073), `gedo gc` (FEAT-087) and the hosting integration.
- Called by `gedo-app` use cases (ingest, publish, graft, status) and, through the CLI's `--json` output (ADR-0013), by tools built on Gedo.
- Persists through the write-ahead log, object store and reference store ports; reads identity results through `IdentityIndex`.
